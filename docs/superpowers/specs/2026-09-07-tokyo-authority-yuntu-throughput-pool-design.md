# 东京权威池与云途本地吞吐选择设计

## 状态

设计草案，等待用户审阅。本文只定义池子同步、硬门槛、吞吐选择和清理规则，不执行 VPS 部署或代码修改。

## 1. 背景与问题

当前云途运行在 `upstream-consumer` 模式，池子信息来自上游快照。现有选择逻辑把 IP 质量放在吞吐之前，并且只允许 `trusted`、`observation` 和 `standby` 节点进入本地可连接队列；上游 `candidate` 节点不会进入云途本地测速。

这会产生三个问题：

1. 官网显示速度很高的节点可能没有进入东京/上游池，云途完全测不到。
2. 即使节点已经进入池子，东京或上游测得的指标也不能代表云途实际出口的单连接吞吐。
3. 节点 IP 失效很快时，二次成功确认会拖慢入池，二次失败确认会拖慢出池并占用池位。

## 2. 目标

- 东京成为唯一的池子权威，只上报通过硬门槛的节点。
- 快照最多包含 300 个硬门槛通过节点；不足 300 个时按实际数量上报，不使用未验证节点凑数。
- 东京不上报吞吐结论；云途使用自己的 TUN/出口路径做真实单连接吞吐测试。
- 保留 `trusted`、`observation`、`candidate` 三类来源标签，但让 `candidate` 也能进入云途测试队列。
- 可信池中按云途实测吞吐选择 active 和 standby；可信池为空时使用观察池。
- 硬失败立即出池；活动线路故障切换仍保留短暂防抖，避免瞬时网络抖动造成业务切换。
- 东京和云途定期清理过期节点、配置、探测状态和旧快照。
- 不改变现有 VLESS、Trojan、HY2、7928、双槽 fail-closed 和既有入口管线的安全边界。

## 3. 非目标

- 不把东京的吞吐数据转发给云途。
- 不使用官网 `Speed` 字段作为节点可用或可信证明。
- 不将未通过东京硬门槛的节点直接发送给云途。
- 不因新候选出现就频繁替换健康的 active 节点。
- 不在本阶段改造 3x-ui、nginx、Cloudflare 或现有订阅导出管线。

## 4. 总体架构

```text
VPNGate 官方节点列表
        │
        ▼
东京 local-authority
  拉取、去重、硬门槛测试、IP质量判断、池子分层
        │ 只上报通过硬门槛的节点快照
        ▼
云途 upstream-consumer
  校验快照 → 本地单连接测速 → active/standby 选择
        │
        ▼
双槽 OpenVPN → 127.0.0.1:7928 → VLESS/Trojan/HY2 入口
```

东京负责“节点是否允许被云途测试”；云途负责“节点在云途实际路径上能跑多快”。两端的职责不能互换。

## 5. 东京硬门槛与池子分层

### 5.1 一次完整硬门槛

节点只有一次完整测试通过后，才允许写入上报快照。测试至少包括：

1. OpenVPN 配置可解析且协议/端口受支持。
2. OpenVPN 握手成功并建立 TUN。
3. 通过该 TUN 能查询真实出口 IP。
4. 真实出口国家为日本。
5. 真实出口类型为 `residential`。
6. IP 风险检查没有硬风险，且 `risk_free=true`。
7. 配置内容生成稳定的 `config_hash`。

吞吐不是东京硬门槛的一部分，也不参与东京上报结果。

### 5.2 三类上报节点

三类节点都必须有 `hard_gate=passed`：

- `trusted`：通过硬门槛，且满足东京现有可信池 IP 质量规则。
- `observation`：通过硬门槛，但未达到可信池的 IP 质量/来源排序条件。
- `candidate`：通过硬门槛，但因池容量、轮换或来源排序暂未进入前两类；它是“硬门槛通过、等待云途吞吐测试”的节点，不是未验证节点。

如果东京没有足够的硬门槛通过节点，快照必须少于 300 条。禁止用 `pending`、`not_checked` 或未知 IP 类型节点补满 300 条。

### 5.3 300 条上报上限

东京每轮流程为：

```text
拉取官方全集
→ 预过滤损坏/重复/不支持配置
→ 对候选逐个执行一次完整硬门槛
→ 只保留 hard_gate=passed
→ 按 IP 质量、最近验证时间、故障域分散和轮换公平性排序
→ 最多取 300 条
```

官方页面的速度字段可以仅作为东京安排硬门槛测试顺序的提示，但不得写入快照作为吞吐结论，也不得代替真实出口硬门槛。

为避免固定前 300 条长期垄断，未进入快照但仍存在于官方列表的节点应按轮次轮换测试。节点只要通过硬门槛，就有机会进入后续快照。

## 6. 快照协议

快照应采用原子写入、递增序列和配置哈希校验。每个节点至少包含：

```text
node_id
config_text 或受管配置引用
config_hash
upstream_pool_state: trusted | observation | candidate
hard_gate: passed
hard_gate_checked_at
hard_gate_expires_at
actual_country
actual_ip_type
risk_free
ip_quality_score
source_seen_at
```

快照顶层至少包含：

```text
schema_version
sequence
generated_at
source_instance
trusted_ids
observation_ids
candidate_ids
```

快照不包含云途吞吐字段。云途自己的吞吐结果保存在本地运行态，不能回写成东京权威数据。

## 7. 云途本地吞吐选择

### 7.1 本地测试

云途接收三类硬门槛通过节点后，按批次执行单连接吞吐测试：

- 每轮最多测试 10 个 `candidate`。
- 优先未测试节点，其次是本地测速结果已过期的节点。
- 每个节点首次通过硬门槛后只需要一次完整吞吐测试即可进入本地排序。
- 后续测速用于更新性能观测，不再作为“第二次成功才能入池”的门槛。
- 记录 `local_download_mbps`、`local_measured_at`、`local_probe_bytes`、`local_probe_path` 和结果有效期。

本地测试至少应绑定具体 TUN/槽位并验证出口没有回落到云途默认公网。吞吐测试失败不改变东京的 `hard_gate` 结论，但该节点不能进入云途 active/standby。

### 7.2 active/standby 选择

推荐选择顺序：

```text
可信池中本地吞吐最高       → active
可信池中本地吞吐第二高     → standby
可信池只有一个             → observation 中最高者补 standby
可信池为空                 → observation 中最高者 active/standby
```

`candidate` 经过云途本地测试后，保留 `upstream_pool_state=candidate`，但进入独立的本地性能候选集合。若可信/观察池不足，或 candidate 的实际吞吐明显高于当前节点，它可以参与 active/standby 竞争；这不会篡改东京的源池标签。

standby 在吞吐接近时优先选择不同 ASN、运营商或网段的节点；没有可分散的节点时才退回纯吞吐排序。

### 7.3 活动粘性

吞吐排序用于初选、补备和故障切换，不用于每次刷新后立即换 active。健康 active 只有在以下情况才切换：

- active 硬失败或连续健康探测失败；
- active 吞吐低于明确的最低可用线；
- 新节点在满足最短保持时间后，吞吐达到明确的超额阈值。

这样可以同时实现吞吐优先和避免节点频繁更换。

## 8. 出池与失效策略

### 8.1 立即出池的硬失败

以下事件一次发生即可从云途可选池移除，并记录原因：

- OpenVPN 配置无法启动或 TUN 建立失败。
- 真实出口无法查询。
- 真实出口不再是日本或 residential。
- 出现硬风险。
- 配置哈希不匹配或快照节点已被撤销。

节点进入短期 cooldown，防止后台立即重复拨号；cooldown 不是第二次复核。

### 8.2 软失败

单次临时超时、Cloudflare 测速端点失败或瞬时丢包，不直接认定 IP 失效。可以将节点立即从本轮 active/standby 候选中移除，并进行一次轻量连接确认；确认成功则恢复，确认失败再进入 cooldown。

池子出池阈值和 active 故障切换阈值分离：池子可以立即标记失效，线上 active 切换仍要避免单个瞬时错误引发业务抖动。

## 9. 定期清理

### 9.1 东京

- 每次成功刷新官方列表后，只保留当前仍存在且硬门槛状态有效的节点。
- 官方列表中消失、硬门槛失败或配置哈希变化的节点不进入下一快照。
- 只保留当前快照和上一份快照；旧快照不累积。
- 删除不在当前/上一快照中的配置文件和探测状态。
- 清理已过期的硬门槛记录、失败冷却记录和旧日志。
- 若官方 API 整体失败，不发布空快照；保留上一份有效快照并标记源不可用。

### 9.2 云途

- 应用有效新快照后，删除不在快照中的非活动节点及本地测速记录。
- 快照撤销的 active 节点标记 `draining`，不再建立新的备用隧道；新备用验证通过后排空旧槽。
- 不在当前快照中的节点不得新建隧道，即使本地曾经测速很高。
- 清理与当前 `config_hash` 不匹配的本地探测状态。
- 只保留当前快照、上一快照和有限的本地测速摘要；日志使用大小/天数上限轮转。
- 云途无法取得新快照时，保留最后一份未过期快照；快照完全过期后停止接纳新节点，但不因源站短暂故障主动清空健康 active。

硬门槛的有效期应绑定刷新周期，而不是永久有效。节点超过有效期后不能继续作为新 active/standby，必须等待东京重新上报。

## 10. 验收标准

### 东京

- 快照中的每个节点都有 `hard_gate=passed`、验证时间、过期时间和配置哈希。
- `trusted_ids`、`observation_ids`、`candidate_ids` 互不重复，且全部属于快照节点集合。
- 快照节点数不超过 300；通过数不足时不补未验证节点。
- 官方列表刷新后旧节点、旧配置和旧探测状态能够按规则清理。
- 官方 API 暂时失败不会发布空快照。

### 云途

- 能消费东京快照并拒绝过期、序列回退、哈希错误和 `hard_gate` 非通过节点。
- candidate 按每轮 10 个进入本地单连接测速队列。
- active/standby 按云途实际吞吐选择，并记录本地测速时间和来源。
- 可信池为空时能从 observation 正常补位。
- 硬失败一次即可从可选池移除，且不会回落到云途默认公网。
- 双槽、7928、VLESS/Trojan/HY2 和现有服务无回归。
- 快照过期、节点撤销、active 排空和 reboot 恢复均通过验证。

## 11. 实施顺序

1. 等东京新版 VPNGate 部署完成，先只读确认现有入口、x-ui/nginx、TUN 和数据目录。
2. 在东京实现硬门槛一次通过、三类池分层、最多 300 条快照和清理机制。
3. 在东京验证快照中不存在未通过硬门槛的节点，再切换云途快照来源。
4. 在云途实现 candidate 批量本地单连接测试、吞吐排序、active/standby 选择和本地清理。
5. 先观察一个完整刷新周期，确认池数量、吞吐、节点 churn、fail-closed 和入口回归。
6. 通过验收后，再更新运维说明和交接记录。

本设计批准前不执行代码修改、VPS 部署、服务重启或池策略切换。
